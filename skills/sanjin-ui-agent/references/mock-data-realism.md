# Mock 数据真实性

S2 写页面时必读。原型的说服力有一半来自数据长什么样——布局再对，只要表格里是「任务A / 任务B / 任务C，成功率 99.9%」，评审的人一眼就知道这是假的，也没法在上面做真实判断。

真实感不是目的，**暴露真实问题**才是：等长的假数据永远不会撑破列宽，平均分布的假状态永远不会让你发现异常态难以扫描。

## 硬规则

### 1. 不使用任何真实内部数据

mock 数据一律虚构。不得复制生产库、真实工单、真实客户名、真实员工姓名、真实手机号与邮箱、内部域名、内部 IP 与集群地址。需要「看起来是内部系统」的质感时，用虚构但符合命名习惯的字符串。

这是合规底线，优先级高于本文件其它所有规则。

### 2. 命名要有领域质感

| 反例 | 正例 | 为什么 |
| --- | --- | --- |
| 任务A / 任务B / 任务1 | `dwd_order_detail_inc_d`、`ads_user_profile_full` | 真实调度任务是有命名规范的 |
| 张三 / 李四 / 用户1 | 按业务域取：`陈立文`、`周敏`，或直接用工号 + 姓氏 | 占位名字是最明显的 Tell |
| 示例科技 / Acme / 测试租户 | `云岚数据`、`衡石智能`（虚构但像真的） | 「示例」两个字等于告诉别人这是假的 |
| 集群1 / 默认集群 | `bj-prod-03`、`shanghai-batch-01` | 环境名带地域与用途才像运维视角 |
| 错误 / 失败原因 | `Executor lost: Container killed by YARN for exceeding memory limits` | 真实报错有结构、有来源 |

不确定某个领域怎么命名时，看 design-spec 第 6 节的字段口径反推，或者问一句，不要退回「任务A」。

### 3. 数值不能完美

- **禁止完美百分比**：`99.9%`、`50%`、`100%`、`0%` 全部避免（真的是 0 或 100 的边界值除外，且应有意为之）。用 `97.3%`、`46.8%`。
- **禁止整百整千**：`1000`、`5000`、`100000` → `1,043`、`4,872`、`96,318`。
- **量级要跨档**：一列数值不能全在同一数量级。真实数据总有几条大得离谱、几条小得可疑。
- **要有长尾**：多数条目正常，少数异常。不要让每一行都很有戏剧性。

### 4. 时间不能等距

- 时间戳不能正好每条差 1 小时、不能全在同一秒。
- 执行时长不能全是整分钟；`00:03:47` 比 `00:05:00` 可信。
- 调度时间要贴合 cron 习惯（整点、半点、凌晨 2–5 点批量），但实际完成时间要有偏移。
- 不出现未来时间；「更新时间」必须早于当前。
- 不用 `2024-01-01`、`2026-01-01` 这类明显的起始日。

### 5. ID 不能连续自增

`1 / 2 / 3` 和 `uuid-0000-0001` 都是 Tell。用有前缀的业务 ID（`JOB-20260918-4471`）或不连续的雪花号。

### 6. 必须包含边界样本（硬规则）

列表和表格的 mock 数据里**至少各有一条**：

- 超长文本（比列宽长一倍以上，用来验证截断与 tooltip）；
- 空值或未知（`--` / `未采集`，用来验证空值占位而不是显示 `null`）；
- 极端数值（特别大或特别小，用来验证数字对齐与单位换行）。

这三条不是为了好看，是为了在 S3 之前就把布局问题暴露出来。少了它们，S3 的视觉验收是在理想数据上做的，接真实数据必崩。

### 7. 状态分布按真实比例

不要为了「展示所有状态」给每种状态平均分配一条。真实的任务列表里失败是少数，待审批是少数。

按业务合理比例造：比如 40 条任务里 3 条失败、2 条重跑中、其余成功。这样才能检验「异常在长列表里是否扫得出来」——这恰恰是 B 端列表设计的核心问题，平均分布会让它完全失效。

### 8. 数据量要够触发真实形态

列表和表格的 mock 条数要能触发 design-spec 里定义的分页或滚动策略。只给 5 条，就验证不了固定列、横向滚动、分页器和虚拟化。

参考量级：前端分页给 40–80 条，服务端分页给到至少跨 3 页，宽表列数按 design-spec 实际列清单给全。

### 9. 验收用例必须能走到（硬规则）

design-spec 第 11 节写了的每条验收路径，mock 里必须真有一条数据能触发它。写了「筛选已暂停且无数据」，就不能在规则表里塞两条已暂停记录；写了「我负责的任务」，数据里就要有 `owner` 字段，筛选必须真正过滤，不能只换 UI 高亮。

否则 G1 过了、G2 脚本也过了，这条用例在浏览器里永远验不到。

## 口径一致

mock 数据的字段名、类型、单位、精度必须与 design-spec 第 6 节一致，并在 S4 的 `HANDOFF.md` 第 5 节如实登记。

两处对不上时以 design-spec 为准并修正 mock，不要反过来改 spec 迁就已经写好的假数据。

## 组织方式

mock 集中放在 `src/mock/`，按数据对象分文件，不要散落在组件里。

理由是 S4 要在 `HANDOFF.md` 里写明「改哪一层即可接真实接口」——mock 混在 JSX 里，这句话就没法写，下游只能全文搜索。

## 自检

- [ ] 无真实内部数据、真实人名公司名、真实联系方式。
- [ ] 无「任务A」「示例」「测试」「Acme」「张三」类占位命名。
- [ ] 无完美百分比、无整百整千、数值跨量级且有长尾。
- [ ] 时间戳不等距、无未来时间、执行时长非整分钟。
- [ ] ID 非连续自增。
- [ ] 每个列表含超长文本、空值、极端值各至少一条。
- [ ] 状态按真实比例分布，非每种一条。
- [ ] 条数足以触发 design-spec 定义的分页或滚动策略。
- [ ] 第 11 节每条验收用例都能用当前 mock 走到。
- [ ] 字段名、单位、精度与 design-spec 第 6 节一致。
- [ ] mock 集中在 `src/mock/`，未散落在组件内。
