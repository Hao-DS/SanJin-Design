# Visual Quality Hard Rules

本文件是「SanJin-UI-Agent」技能的**视觉品质硬规则**。生成或改版任何 UI / HTML 原型前必须读取；交付前必须逐条验收。未通过则修订后再交付。

视觉气质以 `references/DESIGN.md` 为准；本文件补充「什么算不合格」与「如何修」。

## 0. 总原则

1. **先像工作台，再像界面**：信息可扫、操作可找、状态可读。
2. **克制即高级**：用对齐、层级、留白，不用装饰堆砌。
3. **DESIGN 定貌，选定栈实现**：颜色/圆角/字号跟 DESIGN.md；组件 API 跟当前选定实现库（未选择则默认 Semi Design）。
4. **本文件判合格，`ui-judgment/` 给方法，`console-craft.md` 给控制台长什么样**：清单说「什么算不合格」；结构、对齐、密度怎么落，读 `references/console-craft.md`。

## 1. 首屏预算（硬）

首屏只允许：

| 允许 | 不允许 |
| --- | --- |
| 页面标题 + 1 行辅助（更新时间/影响范围） | 长说明段落、产品故事文案 |
| 1 条筛选条 | 双层筛选 + 侧栏过滤器同时占满首屏 |
| ≤4 个 KPI | 5+ KPI、统计条、进度墙 |
| 1 个主内容（表或图） | 首屏同时塞表+图+说明卡 |

**失败判定**：去掉导航后，首屏仍像营销页 / 仪表盘拼贴，即不合格。

## 2. 层级与对齐（硬）

- 同一行控件：高度统一（默认 32px），基线对齐。
- 同级标题字号一致；KPI 数字必须明显强于标签。
- 卡片/面板左右边距与页边距网格对齐；禁止「差一点」的错位。
- 表格工具栏、筛选操作区右对齐策略全页一致。

## 3. 颜色与强调（硬）

- 每屏 **1 个** primary 实心按钮。
- Primary 仅用于：主操作、链接、选中、焦点。
- 语义色只表示状态，不作为大面积背景装饰。
- 禁止：紫粉渐变 AI 风、多强调色并存、大面积品牌色铺底。

## 4. 表面与深度（硬）

- 内容区 flat-first：白底 + 1px 边框 + 间距。
- 阴影仅用于浮层（Dialog / Drawer / Dropdown）。
- 禁止：玻璃拟态、多层投影、霓虹光晕、营销 Hero 渐变。

## 5. 密度与噪音（硬）

- 禁止 chip / Tag 瀑布（筛选摘要 ≤ 一行或 ≤ 3 个 Tag）。
- 禁止无任务意义的 icon 行、徽章贴片、悬浮 callout。
- 表格操作列用 link，不用一排彩色按钮。
- 说明文案默认折叠或放次要色；不要与 KPI 数字抢视线。

## 6. 状态完整性（硬）

用户要求状态时，主内容区应清晰表达：

- loading / empty / error / no-permission / success feedback

状态必须**文字可读**，不可只靠色块。

## 7. 原型品质（硬）

### Semi / Ant / TDesign 工程原型

1. 仅使用选定栈组件；先 MCP 取证再写代码。
2. 壳层布局用 DESIGN.md token（canvas / surface / spacing），少写随意 hex。
3. 禁止把其它库的 class 或皮肤硬拷进页面。
4. 主任务必须有可操作闭环；loading、empty、error、no-permission 等状态只按用户要求实现。
5. 交付前运行 `scripts/validate_prototype.py`，再对照下方清单自检。

## 8. 视觉验收清单（交付前必过）

复制到输出末尾，逐项勾选：

```text
[ ] 首屏仅：标题 / 筛选 / ≤4 KPI / 主表或主图
[ ] 仅 1 个 primary 实心按钮
[ ] 无渐变 Hero / 玻璃拟态 / 紫粉 AI 装饰
[ ] 无 chip 瀑布、双主按钮、彩色操作列
[ ] KPI 数字层级明显强于标签
[ ] 同级控件对齐，间距为 8/16/24
[ ] 标题 / 筛选 / 主表（及 KPI）左缘对齐，差 ≤ 2px
[ ] 数字列 tabular-nums 且右对齐；ID / 时间用等宽
[ ] 状态有文字（非纯色块）
[ ] 未增加用户未要求的状态演示
[ ] 同一工作区同一方向只有一个主滚动容器，固定区未遮挡末条内容
[ ] 组内间距小于组间间距；同类关系用同一档位
[ ] 仅使用选定实现栈组件
[ ] 颜色与圆角符合 DESIGN.md
[ ] 已完成一条主任务闭环，状态范围与用户要求一致
[ ] evidence.json 已记录组件证据；validate_prototype.py 无错误
```

任一项未勾选 → 先修再交。

## 9. 常见不合格 → 修法

| 现象 | 修法 |
| --- | --- |
| 页面「灰扑扑」但乱 | 减少区块数；统一 24 间距；收紧首屏；按 `console-craft.md` 改成表优先或齐平，不要悬浮卡墙 |
| 看起来像模板站 | 去掉装饰卡与多余边框阴影；强化 KPI/表 |
| 标题、筛选、表格左右错开 | 去掉额外 padding；用 `.page` 同一列；测 `left` 差 ≤ 2px |
| 数字对不齐、ID 像正文 | 数字列加 `.tabular` 右对齐；ID/时间加 `.mono` |
| 按钮太多抢视线 | 只留 1 个 primary；其余 default/link |
| AI 面板很「赛博」 | 去掉渐变与光效；用 surface + 边框 |
| 表格很挤 | 工具栏分区；固定列；操作改 link |
| 自定义 CSS 过多 | 删回选定栈默认主题 + DESIGN token 壳层 |

## 10. 走查维度（清单之外）

用户要求走查、或交付前自查时，先跑确定性检查，再看清单覆盖不到的语义问题。

**第 0 步：别用人脑做机器的事。** 先运行 `scripts/validate_prototype.py`，它命中的跨栈导入、证据缺失、渐变/玻璃拟态等直接进「必改」。人只看它抓不到的：

1. **取值语义**：用了合法 token，但语义错位（正文用了 error 色、普通操作用了危险样式）。
2. **组件选型**：该用选定栈现成组件的地方是否手搓了一套；是否混入了非选定栈的 API 或皮肤。
3. **层级是否由任务决定**：主次是否有产品依据，还是靠字号和颜色硬撑（判据见 `references/ui-judgment/hierarchy.md`）。
4. **布局与滚动**：滚动归属是否唯一、固定区是否遮挡内容、间距档位是否跳跃（判据见 `references/ui-judgment/layout.md`）。
5. **状态完整性**：需求要求的状态是否齐全可区分，是否补了用户没要的状态（判据见 `references/ui-judgment/states.md`）。
6. **响应式**：是否只验证了单一桌面宽度；0 条 / 1 条 / 大量数据下是否都成立。
7. **动效必要性**：每个动效是否表达真实信息，是否有 reduced motion 降级（判据见 `references/ui-judgment/motion.md`）。

**输出要求**：按「必改 / 应改 / 建议」分组，每条给**位置（文件:行）+ 现状 + 为什么不符 + 怎么改**。不输出「整体感觉不够精致」这类无法落地的话，也不顺手重写评审范围之外的代码。

评审现有界面时，每条发现还须通过 `design-evidence-gate.md` 的证据门禁。
