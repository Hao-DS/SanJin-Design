# 界面状态

**管什么**：这一版原型要展示哪些状态，每个状态用什么内容、什么载体、什么反馈样式。

**何时读**：设计 loading、empty、error、success、权限、选择或控件状态时。

**不管**：数据与系统行为由业务规则定义；准确颜色取值读 `references/DESIGN.md`；AI 特有的来源、时效与不确定性读 `references/ai-trust-and-states.md`；权限与审计模式读 `references/b2b-operational-patterns.md`。

## 确定要做哪些状态

### Do

- 只做需求明确要求、且**有可见差异**的状态。
- 需求没说明的状态不补；需要演示时用 mock 数据和本地交互，并标为模拟。
- 明确每个状态的**影响范围**：局部出现 loading、error 或权限限制时，只细化对应区域。

### Don't

- 不为凑齐状态清单，设计没有界面差异的组合。
- 不根据组件名称、颜色或技术术语反推产品状态。
- **不主动增加状态切换器、演示菜单或状态陈列页**（这是 `SKILL.md` 的硬要求）。
- 任务失败、影响严重、无权限是三件事，不用一个状态同时表达。

### 设计原则

原型只表达需求已确认的界面状态，不设计真实的数据或系统行为。常见状态按类型分：

| 类型 | 按需展示的常见状态 |
| --- | --- |
| 内容 | initial、loading、content、empty、partial、error |
| 操作 | idle、submitting、success、failed |
| 控件 | default、hover、focus、pressed、selected、disabled、expanded、collapsed |
| 访问 | allowed、read-only、permission denied、blocked |
| 选择 | 未选、部分选中、全选 |

## 处理加载、空、错误与受限

### Do

- loading 用**具体文字**：「正在保存」「正在生成报表」，不是笼统的「加载中」。
- 结构稳定时用骨架屏；局部更新时只在对应区域显示进度。
- loading、empty、error、content 之间切换时**保持页面结构稳定**，不要让整页高度跳动。
- **首次空态**说明用户能做什么；需求已定义创建入口时才给入口。
- **无结果空态**保留当前搜索与筛选条件，让用户知道是被什么筛掉的。
- 只有部分内容返回时，继续显示已返回的部分，并明确标出哪些缺失。
- 权限或前置条件受限时说明限制本身；需求已定义申请或返回方式时才给入口。
- 错误提示说明**发生了什么、影响什么**。字段错误紧邻字段，区域错误留在区域内，只有整页不可用才用整页错误。

### Don't

- loading 尚未结束时不要闪出空态。
- 不把所有空态统一写成「暂无数据」——首次空、筛选无结果、无权限是三种不同的话。
- 不把权限限制伪装成空数据，不把输入无效当成执行失败。
- 不伪造未确认的技术原因（「服务器开小差了」）。
- 错误文案不归咎用户。
- 后续仍需查看的说明和帮助，不能只出现在首次空态里。

### 设计原则

反馈只覆盖受影响的范围。权限、前置条件和错误三者不能混用：

- **无权限**：说明谁不能做这件事；
- **前置条件**：说明还缺什么才能做；
- **错误**：说明这次任务没有完成。

## 表现操作与控件状态

### Do

- default 状态就让入口可识别，hover 只做补充反馈。
- focus 必须可见；pressed 在按下时出现；selected 表示已选择；disabled 表示当前不可操作。
- loading 期间保持控件**尺寸稳定**，不要因为出现转圈图标导致按钮变宽、行高跳动。
- 需求明确定义了操作结果时，才分别展示成功与失败；未定义时在交付说明里标为待确认。
- 只有需求已确认「删除已有数据、撤销权限、丢弃用户内容」时，才使用危险样式。

### Don't

- 不用 hover 作为唯一入口或唯一反馈。
- 不移除焦点轮廓后又不提供替代表达。
- **不用 disabled 掩盖权限或校验问题**——用户需要知道为什么不能点。
- 不显示需求没有定义的百分比、剩余时间、取消入口。
- 不因为按钮上写着「删除」就自动套危险样式；由已确认的后果决定。

### 设计原则

控件状态表达当前可见的交互结果，不承担产品逻辑。组件已有状态样式时直接沿用，不在页面里重新拼一套。

## 选择反馈载体

### Do

按**影响范围、持续时间、是否需要用户决策**三个维度选：

| 情况 | 载体 |
| --- | --- |
| 紧凑、无需操作的状态展示 | 状态标签（文字 + Tag，可加色点） |
| 字段级问题 | 字段旁提示 |
| 区域级问题，需要解释或恢复动作 | 区域内提示条 / Alert，持续可见 |
| 已完成、无需决策的轻反馈 | Toast |
| 需要用户确认后果才能继续 | Dialog，并展示影响范围 |

### Don't

- 不在业务页面手拼状态标签的文字、背景、描边和尺寸；用选定栈的组件。
- 需要复制、比较或持续处理的问题不能只放 Toast（会自动消失）。
- 已发生且无需选择的结果不要用 Dialog 打断。
- 需要解释或恢复动作时，不用状态标签代替提示条。
- **任何状态都不能只用颜色表达**，必须同时有文字、图标或结构差异（`SKILL.md` 硬要求）。

### 设计原则

高风险批量操作、权限变更、导出和自动执行必须展示影响范围并确认，见 `references/b2b-operational-patterns.md`。

## 交付前验证

- 需求涉及的 loading、empty、error、success 是否都能单独查看；
- 需求涉及的控件状态是否可区分；
- 状态切换时布局和控件尺寸是否稳定；
- 反馈是否被限制在受影响区域内；
- 文案、载体和颜色是否与状态含义一致；
- 原型数据和演示状态是否已明确标为模拟。

不要把所有状态组合画成独立页面，也不要为了演示样式补写产品逻辑。
