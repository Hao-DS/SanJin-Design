# 快速模式

默认流程：F1 理解任务 → F2 Figma 静态稿 → F3 设计自检 → 人工评审、优化与确认 → F4 交互实现与验证。用户最初要求完整页面，也先交付可审阅设计稿。只要设计稿时止于设计交付。

仅维护 design/pipeline.json，不默认写 design-spec、polish-log、HANDOFF 或长篇报告。

## F1 · Design Read

简要回述角色、主任务、页面范围、首屏主内容、关键状态和假设。只问会改变主任务、页面范围或高风险行为的必要问题；其余按安全默认值推进。此时不选实现组件，也不写页面代码。

## F2 · Figma 静态稿

- 创建可编辑 Frame，覆盖目标页面和关键状态。使用虚构但有领域质感的数据，边界样本应能暴露布局问题。
- 先定信息层级、工作区结构和主操作，再处理视觉。读取 DESIGN.md、console-craft.md 和按需判断规则。
- 高风险动作用单独状态 Frame 展示影响范围、风险说明和确认文案。静态稿不要求可点击，也不启动前端工程。

## F3 · 设计自检与人工确认

按 visual-quality.md 检查层级、对齐、密度、对比度、关键状态和跨页一致性，修正明显问题后交付 Figma 链接、Frame 名称、审阅版本、假设与待确认项。

收到修改意见时更新 Figma，标记新审阅版本，重新提交。明确收到对当前版本的确认前不得执行 F4。内部自检、链接已发送、用户未回复都不能通过此门禁。记录确认人、时间、Figma 文件与 Frame、审阅版本和反馈处理结果；未确认时阶段为 awaiting_review。

## F4 · 交互实现与验证

核对确认版本后，选择实现栈并取组件证据。按确认稿搭建页面、关键状态与主任务闭环。构建，运行 validate_prototype.py，在浏览器验证主流程、高风险确认与恢复路径。需要改变确认稿中的设计决定时退回 F2 并重新确认。

## 需求变化

| 变化 | 退回 |
| --- | --- |
| 主任务、页面、关键状态、结构或视觉决定 | F2，重新提交确认 |
| 仅实现细节且不影响确认稿 | F4 |

下游阶段标为 stale，不复用旧确认。
