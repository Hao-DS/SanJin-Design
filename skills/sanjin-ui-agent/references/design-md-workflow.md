# DESIGN.md 证据化沉淀流程

仅在用户明确要求设计规范/设计系统，或项目约定需要同步设计契约时使用。目标是记录真正治理产品的设计语言，而不是汇总页面中出现过的所有值。

## 模式

### 仓库模式（默认）

从目标产品的源码和已有文档提炼或更新项目根 `DESIGN.md`。多产品仓库必须先确定目标产品，不把多个设计系统混写。

### 视觉证据模式

适用于只有截图、Figma 或可访问页面而缺少源码的情况。输出必须标记为“重建设计规范草案”；截图只能支持视觉判断，不能证明内部 Token 名、组件归属或设计动机。

## 证据账本

写文档前先在工作上下文中记录：

```text
角色 → 值/规则 → 来源 → 适用范围 → 复现范围 → 置信度
```

按以下顺序取证：

1. 已有 `DESIGN.md`、项目规则和明确设计决策；
2. 被目标产品实际使用的 Token、主题和全局样式；
3. 共享基础组件及其变体；
4. 代表性路由和实际消费者；
5. 页面局部实现。

来源只有在目标产品确实导入、继承、解析或渲染它时才参与。提案、迁移计划、演示、旧系统和同名包默认排除。

## 纳入门禁

只有满足以下条件的内容才写入：

- 能改变具体实现选择；
- 有明确来源和适用范围；
- 系统级规则有设计契约，或由共享拥有者在至少两个已审查表面使用；
- 精确值来自命名 Token、主题配置或可验证计算值；
- 与当前产品实际运行路径一致。

必须排除：

- 从重复字面量推导出的“Token”；
- 将页面局部样式提升为全局规范；
- 把设计偏好、最佳实践或案例皮肤写成产品意图；
- 组件清单、审计过程、未解决问题和无执行意义的描述；
- 为了填满章节而编造的颜色、字号、圆角或品牌性格。

## 文档结构

格式以 `knowledge/design-md/google-spec/docs/spec.md` 为准，最小 frontmatter 为：

```yaml
---
version: alpha
name: <产品名称>
description: <有证据支持的简短描述>
---
```

- 精确规范值写入 YAML；设计意图和使用规则写入 Markdown。
- Token 组使用映射，不使用序列；颜色保持扁平、可导出的命名。
- 字体比例必须写成命名映射，并使用规范字段，如 `fontFamily`、`fontSize`、`lineHeight`、`fontWeight`、`letterSpacing`。
- 仅添加有证据支持的章节，顺序为：Overview、Colors、Themes、Typography、Layout、Elevation & Depth、Shapes、Components、Do's and Don'ts。
- 禁止项只有在项目来源明确禁止时才能写入。
- 不引用外部品牌样例；只依据目标产品证据和本地格式规范。

## 更新规则

更新已有 DESIGN.md 时：

1. 保留现有已接受决策；
2. 对照当前运行路径验证每条拟修改规则；
3. 只有新证据明确替代旧决策时才删除或改写；
4. 页面实现与明确规范冲突时，记录为待修正实现，不用现状覆盖规范；
5. 未获授权时只在交付摘要列出候选决策，不自动改写项目根 DESIGN.md。

## 验证

交付前完成：

- frontmatter 可解析，字段形状符合本地规范；
- 每个 Token 和规则都能回溯到证据账本；
- 删除不改变实现选择的句子；
- 检查章节顺序、重复规则和局部实现误提升；
- 若项目已安装并批准使用 `@google/design.md`，运行 lint 与对应技术栈的 export；不得为了运行命令临时向公网发送项目内容。

报告中说明：目标产品、创建或更新的文件、采用的治理来源、因证据不足而省略的内容、验证结果。视觉证据模式必须注明“重建草案”。
