# 产品需求 → 设计需求（S1）

本文件是流水线 S1 的执行规则。目标是把产品视角的需求，转成设计和实现能直接照着做、并且 G1 门禁能逐条验的**设计需求**。

产物是 `design/design-spec.md`。完整档结构见 `design-spec.template.md`，轻量档见 `design-spec.light.md`。

**默认不要整篇读本文件。** S1 先按 `pipeline.md` 选档位并复制对应模板填写。仅在完整档需要推导步骤、任务流推不出页面、或 G1 自检不过时，再读下面的规则。

**这一阶段不写代码，不选组件，不定视觉取值。** 页面里用什么组件属于 S2（要先取证），颜色字号间距属于 `DESIGN.md`。S1 只回答：有哪些页面、每页解决什么、数据和权限是什么、怎么算做完。

## 输入分层（硬规则）

先把手上的材料切成四类，写进 spec 时不许串味：

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| 事实 | PRD、接口文档、现有页面、截图里明确写着的 | 直接采用，注明出处 |
| 已确认决策 | 用户在对话中拍板的 | 直接采用，注明「本次确认」 |
| 推断 | 材料没写，但由业务常识可唯一推出的 | 采用，**标注为假设**，进假设清单 |
| 缺口 | 材料没写，且存在多个互斥可能 | 不猜，进待确认清单；阻塞实现的才提问 |

把推断写成事实，是 S1 最常见也最贵的错误——它会一路传到开发那里被当成需求实现。

## 执行步骤

### 1. 快照输入

把 PRD 原文、截图、字段表存进 `design/input/`，只读不改。后续任何一条设计需求都要能指回这里的某一处，或指向对话里的某次确认。

### 2. 抽角色与主任务

每个角色写一行：**谁 · 在什么场景下 · 要完成什么 · 什么情况算完成**。

角色超过 3 个时，只保留本次原型要覆盖的。「完成判定」必须是可观察的结果（拿到某个数、某条记录状态变了、某个文件导出了），不能写「提升效率」。

### 3. 写任务流

用文本写，不画图：

```text
运维负责人 · 处理今日失败任务
入口（每日巡检告警邮件）
→ 任务列表页：按「今日 + 失败」筛选
→ 选中若干条 → 查看失败原因（详情抽屉）
→ 批量重跑 → 确认影响范围 → 提交
→ 回到列表，看到状态变为「重跑中」
```

每个主任务一条流。**分支和失败路径也要写**，不能只写幸福路径——G2 要验的闭环就是从这里来的。

### 4. 由任务流推页面清单

**不要把 PRD 的功能列表直接当页面清单。** PRD 写的是能力，页面清单是任务的落点，两者不是一对一：三个功能可能落在同一页，一个功能可能拆成列表页 + 详情页 + 配置页。

推导方式：走一遍任务流，每次「用户需要换一个上下文才能继续」就是一个新页面；只是换了个视图或展开了细节，就是同页内的模块、抽屉或弹层。

清单里每个页面要有：路由、页面名、承接哪个任务的哪一步、进入路径、返回/完成后去哪。**返回路径必须闭合**，没有只进不出的页面。

### 5. 每页定「要回答的问题」

一页只回答一个主要问题，写成一句话。这句话直接决定 S2 的首屏排布，也是 G3 判断层级对不对的依据。

顺带定好首屏预算的取舍：标题行写什么、筛选有哪几个、KPI 取哪几个（≤4）、主内容是表还是图。取不准时按 `ui-judgment/hierarchy.md` 判断，不要靠手感排。

### 6. 抽数据对象与口径

列出页面上出现的每个数据对象、关键字段、类型、单位、精度和统计口径。

口径尤其不能省：「任务成功率」是按任务数还是按执行次数算、分母含不含未开始的、时间范围是自然日还是滚动 24 小时——这些 S2 会直接写进 mock 数据，S4 会交给开发照着接接口。PRD 没写口径就进待确认清单，不要自己定一个看起来合理的。

### 7. 权限与高风险动作

逐条列出：哪些角色看不到什么、哪些操作会改数据或对外产生影响、哪些不可逆。

高风险动作要写明影响范围怎么算、确认要展示什么、失败了怎么办。没有高风险动作就明确写「本次无」，不要留空——留空在 G1 无法区分「没有」和「没想」。

### 8. 逐页列状态

每条状态写清楚：哪一页、哪个区域、什么条件触发、用户看到什么、能怎么恢复。

**每条都要有需求依据。** 依据可以是 PRD 明确要求、任务流里的失败分支、或权限规则推出的必然状态。为了「状态齐全」补一个 PRD 里不存在的空态，会在 G2 被判为超范围实现。

### 9. 收敛假设与待确认

两份清单分开写。假设清单是「我们这么定了，除非你否决」；待确认清单是「必须你来定，我们没定」。待确认项要标出阻塞程度：阻塞 S2 的必须在 G1 之前解决，不阻塞的可以带着往下走。

## 提问规则

只问**会改变任务流或页面清单**的问题，一次最多 3 个，问完就继续。

不问的：能从 PRD 推出的、能用安全默认值兜住的、属于视觉取值的、属于组件选型的、可以先按假设实现再让用户在原型上否决的。

在原型上指着改，比在需求阶段来回问，对用户更省力——这是做可交互原型的意义。所以拿不准的细节优先写成假设带进 S2，而不是停在 S1 追问。

### 10. 验收用例必须可到达

第 11 节每条用例都要能用计划中的 mock 数据走出来。写完后反过来核对：这条操作在第 6 节的数据和第 8 节的状态里，有没有一条真实路径能触发它。

典型失效：写了「筛选已暂停且无数据」，却在规则列表里放了两条已暂停的记录——这条用例在 S2 永远验不到，等于没写。要么改 mock 计划让它到达，要么删掉这条用例。

## 禁止项

- 不臆造字段、口径、权限规则和接口行为。
- 不把 PRD 的功能清单直接抄成页面清单。
- 不在 S1 写组件名、props 和技术选型（S2 取证后才有资格写）。
- 不在 S1 写颜色、字号、间距等取值（`DESIGN.md` 是唯一真源）。
- 不补 PRD 和任务流里都不存在的状态。
- 不把「提升体验」「优化流程」这类无法验收的话写进 spec。

## 现有界面改造

需求是改造已有页面时，S1 之前先过 `design-evidence-gate.md`：只有同时证明设计契约、运行路径和唯一修正的问题，才能作为改造依据写进 design-spec。

改造类 spec 额外要写清：改造范围边界（哪些页面不动）、现有交互里哪些必须保留、迁移或兼容要求。
