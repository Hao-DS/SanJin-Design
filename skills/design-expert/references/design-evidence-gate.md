# 设计问题证据门禁

用于现有界面改进、设计评审、设计系统漂移检查和改稿复查。目标是只报告能够证实的问题，不把个人偏好、代码差异或搜索结果包装成设计结论。

本门禁不限制从零设计中的合理创作。新原型缺少项目契约时，以用户目标、业务约束和 `references/DESIGN.md` 作为默认设计依据；不得声称这些默认值是项目既有规范。

## 先选定审查表面

一次只审查一个可部署产品中的一个连贯任务表面。先从路由和布局追踪到页面组合、共享组件、变体、Token 与样式；名称相似、目录相邻或数值重复不能证明它们属于同一设计系统。

记录：

- 审查表面与用户主任务；
- 生效的设计来源；
- 组件/Token 的拥有者与使用者；
- 已记录的例外；没有则写“未记录”。

## 三重证明

候选问题只有同时通过以下三项，才可成为正式发现：

1. **契约（Contract）**：存在约束该属性与表面的明确设计决定，或同一任务内存在直接的用户可见矛盾。
2. **运行路径（Runtime）**：能通过路由、导入、属性、Token 解析、CSS 继承或实际渲染，证明该实现到达被审查表面。
3. **确定修正（Correction）**：证据能够导出一个明确改法；如依赖已有 Token、变体或组件，必须准确命名。

以下内容只能产生候选，不能单独证明问题：全文搜索结果、重复代码、相似数值、不同实现方式、缺少文档、通用最佳实践。

## 证据类型边界

- 源码可以证明 Token、字体、颜色、间距、布局、文案、组件变体和明确设计契约的违反。
- “层级不清、密度不佳、难以发现、认知负担高”等体验判断，需要截图、实际渲染、用户证据或可复现任务证据。
- 功能故障、数据接线、性能、架构和代码质量不属于设计发现，除非用户明确要求，或设计契约直接约束它。
- 无障碍与 HTML/ARIA 语义仅在用户要求、项目硬规则或交付验收范围内报告。

## 反证复核

报告前重新打开每个引用来源，并主动尝试推翻候选。出现以下任一情况就删除：

- 规则并不约束该属性或表面；
- 运行路径未被证明；
- 差异是已记录的例外或合理状态差异；
- 证据支持多个互斥改法；
- 修正需要臆造产品意图；
- 与另一条发现属于同一根因。

## 输出与实施

最多保留 3 条，按证据强度、用户影响、覆盖范围和修正成本排序。每条必须包含：

- 问题；
- 契约证据；
- 运行路径证据；
- 唯一修正；
- 影响范围；
- 置信度。

没有候选通过时，明确写“未发现有充分证据支持的设计问题”，不要用弱建议凑数。

- 用户只要求评审或诊断：保持只读，先报告发现。
- 用户明确要求修改：只实施已通过门禁且在授权范围内的确定修正；完成后重新验证运行路径与渲染结果。
- 组件 API 证据仍单独记录在原型工程的 `evidence.json`，不要与设计问题证据混为一谈。
